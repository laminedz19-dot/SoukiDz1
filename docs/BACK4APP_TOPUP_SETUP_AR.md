# تشغيل طلبات شحن الرصيد على Back4App

هذا الدليل يطابق مسار الشحن الحالي في `app` و`admin`. **Back4App/Parse هو مصدر الحقيقة** للطلب والقرار والرصيد؛ قاعدة Room كاش محلي فقط.

## 1. إعداد الإعدادات دون تضمينها في المصدر

### محلياً
انسخ `local.properties.example` إلى `local.properties` في جذر المستودع، ثم ضع القيم من لوحة التطبيق في Back4App. يقرأ Gradle الملف تلقائياً عند بناء الوحدتين.

### GitHub Actions
في إعدادات المستودع، أضف Actions secrets بالأسماء التالية:

- `BACK4APP_APP_ID`
- `BACK4APP_CLIENT_KEY`
- `BACK4APP_SERVER_URL`

يستهلكها `.github/workflows/build-two-apks.yml`. إذا لم تكن القيم موجودة، يمكن أن ينجح بناء APK غير مهيأ للاتصال؛ تهيئة التطبيق تتخطى Parse عند غياب App ID أو Server URL، لذلك لا تعتبر ذلك إصداراً صالحاً للإنتاج.

> لا تضع **Master Key** في التطبيق أو `local.properties` أو GitHub Actions. `Application ID` و`Client Key` معرفات عميل تدخل في APK ولا تمنح صلاحية الإدارة وحدها؛ الحماية الفعلية من خلال CLP وACL وCloud Code ودور Admin.

## 2. تجهيز Back4App مرة واحدة

1. أنشئ الجداول المطلوبة قبل تعطيل إنشاء الجداول من العملاء. على الأقل: `_User` (موجود افتراضياً)، `TopUpRequest`, `Wallet`, و`WalletTransaction`.
2. أنشئ Parse Role باسم `Admin`، واجعل صلاحيات الدور غير عامة، ثم أضف إليه حساب الإدارة الأول من لوحة Back4App أو بإجراء آمن من الخادم.
3. انشر `cloud/main.js` في Cloud Code **قبل** تجربة إرسال الطلبات أو مراجعتها.
4. أغلق صلاحيات الكتابة العامة، واستخدم صلاحيات الاستعلام المناسبة للمستخدم المسجّل مع ACL لكل سجل. يحتاج المستخدم إلى الاستعلام عن سجلاته فقط، بينما ترى الإدارة السجلات الممنوحة لدور `Admin`. لا تفتح قراءة عامة لـ`TopUpRequest` أو `Wallet`.

## 3. تدفق الشحن الحالي

1. يسجل العميل الدخول إلى Parse (أو يستخدم جلسة زائر Parse)، ويُرسل REST session token تلقائياً.
2. يرفع التطبيق الحد الأدنى **200 دج**، مزود الدفع المعتمد، المرجع/الوصل، ورابطاً مرجعياً إلى `_User` الحالي.
3. يتحقق Cloud Code من ملكية الطلب والمبلغ والمزود والمرجع، ويثبت الحالة `PENDING` ويضع ACL للمالك ودور الإدارة. لا يملك التطبيق حق تعديل الحالة أو المبلغ أو المالك بعد الإنشاء.
4. تطبيق الإدارة يستعلم عن Back4App دورياً ويعرض حالات التحميل/الخطأ؛ الاعتماد والرفض يمران عبر `approveTopUpRequest` و`rejectTopUpRequest` فقط.
5. الاعتماد يحدّث محفظة Back4App ويكتب معاملة المحفظة في Cloud Code. تطبيق العميل يزامن حالة الطلب والرصيد من Back4App؛ لا يُضاف الرصيد في جهاز المشرف.

## 4. خصوصية صورة الوصل

صور الطلبات الجديدة تُضغط إلى Data URI محدود الحجم وتُحفظ **داخل سجل `TopUpRequest` نفسه**، فتحميها ACL السجل، ولا تُرفع كملف Parse عام. يقبل الخادم حتى 300,000 حرف لحقل الصورة، ويحاول التطبيق ألا يتجاوز 280,000 حرف.

**تنبيه ترحيل:** روابط Parse File العامة المخزنة في الطلبات القديمة تظل قابلة للفتح لمن يملك الرابط. قواعد ACL على سجل الطلب لا تحمي ملفاً عاماً منفصلاً. راجع الطلبات القديمة واحذف/استبدل وصولاتها العامة وفق إجراءات Back4App قبل الاعتماد على الخصوصية الجديدة.

## 5. الاختبار بعد النشر

1. أنشئ مستخدم عميل، ثم أرسل طلباً بقيمة 200 دج مع مرجع صحيح.
2. تحقق من ظهور سجل `TopUpRequest` بحالة `PENDING` ووجود pointer صحيح إلى `_User` وACL مناسب.
3. سجّل الدخول بتطبيق الإدارة بحساب عضو في Role `Admin`، وتحقق من ظهور الطلب ومعاينة الوصل.
4. ارفض طلباً تجريبياً، ثم أرسل طلباً آخر واعتمده. تحقق من أن طلباً واحداً فقط انتقل إلى `APPROVED` وأن رصيد العميل ومعاملة `WalletTransaction` ظهرا مرة واحدة.
5. جرّب الحساب العادي: يجب أن يفشل استدعاء Cloud Function للإدارة، ويجب ألا يستطيع تعديل الرصيد أو الحالة مباشرة عبر REST.

## ملاحظة تشغيلية

التعديلات البرمجية لا تنشر Cloud Code أو تغيّر إعدادات Back4App تلقائياً؛ يلزم نشر الملف وإعداد Role/CLPs في لوحة Back4App. تعذر التحقق من أسماء Secrets الحالية في GitHub بسبب رفض صلاحية API (`403`)، لذا تحقق من إضافتها بنفس الأسماء أعلاه قبل بناء إصدار الإنتاج.
